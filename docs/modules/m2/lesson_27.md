## Розминка: сходи { #stairs }

Перш ніж повернутися до водія — маленька задача, на якій добре видно, де звичайна рекурсія марнує час.

Скількома способами можна піднятися на `n` сходинок, якщо за один крок долаєш 1 або 2 сходинки? Останній крок був або на 1 сходинку, або на 2. Тож способів дійти до `n` стільки, скільки до `n - 1`, плюс стільки, скільки до `n - 2`:

`stairs(n) = stairs(n - 1) + stairs(n - 2)`, а `stairs(0) = 1` (нуль сходинок — один спосіб: ти вже нагорі) і `stairs(1) = 1`.

### Звичайна рекурсія рахує те саме знову й знову

```python
calls = 0


def stairs(n):
    global calls
    calls += 1
    if n <= 1:
        return 1
    return stairs(n - 1) + stairs(n - 2)


print(stairs(30), calls)
```


### Мемоізація: порахувати раз, потім підглянути

Заведемо словник. Перед обчисленням `stairs(n)` перевіряємо, чи `n` уже в ньому; після обчислення — записуємо результат:

```python
calls = 0
memo = {}


def stairs_memo(n):
    global calls
    calls += 1
    if n in memo:
        return memo[n]
    if n <= 1:
        result = 1
    else:
        result = stairs_memo(n - 1) + stairs_memo(n - 2)
    memo[n] = result
    return result


print(stairs_memo(30), calls, len(memo))
```

```text
1346269 59 31
```

59 викликів замість 2 692 537, і це разом із тими, що лише підглянули в словник. Справжніх обчислень 31, по одному на кожне `n` від 0 до 30. Решта 28 викликів знайшли готову відповідь. Готовий варіант того самого — `@functools.cache` з уроку 19:

```python
from functools import cache


@cache
def stairs_cached(n):
    if n <= 1:
        return 1
    return stairs_cached(n - 1) + stairs_cached(n - 2)


print(stairs_cached(30), stairs_cached.cache_info())
```

```text
1346269 CacheInfo(hits=28, misses=31, maxsize=None, currsize=31)
```

`misses=31` — справжні обчислення, `hits=28` — відповіді з кешу, разом ті самі 59.

!!! tip "Те саме в бекенді: кешування"
    Ідея «не рахуй те саме двічі» трапляється в бекенді на кожному кроці. Результат повільного запиту до бази даних чи до чужого API зберігають і віддають наступного разу, не питаючи знову. Це називають **кешуванням**, і в уроці 31 ти робитимеш його через Redis.

### Таблиця: від найменшого випадку вгору

Можна піти навпаки: не від `n` униз, а від нуля вгору, заповнюючи список циклом. `table[0] = 1`, `table[1] = 1`, а кожна наступна комірка — сума двох попередніх, до `table[n]`:

```python
def stairs_table(n):
    table = [0] * (n + 1)          # n + 1 комірка: від 0 до n
    table[0] = 1
    if n >= 1:
        table[1] = 1
    for i in range(2, n + 1):
        table[i] = table[i - 1] + table[i - 2]
    return table[n]


stairs_cached.cache_clear()
try:
    stairs_cached(3000)
except RecursionError as error:
    print("кеш:", type(error).__name__, error)
print("таблиця:", len(str(stairs_table(3000))), "цифр у відповіді")
```

```text
кеш: RecursionError maximum recursion depth exceeded
таблиця: 627 цифр у відповіді
```

Рекурсії тут немає, тож немає й `RecursionError`. Таблиця легко рахує `n = 3000`, а рекурсія з кешем упирається в межу глибини. Кеш прибирає **повторну роботу**, але не **глибину**.

### Два питання перед будь-якою таблицею

1. **Що означає одна комірка?** — «`table[i]` — скільки способів піднятися на `i` сходинок».
2. **Як порахувати комірку з попередніх?** — «`table[i] = table[i - 1] + table[i - 2]`».

Якщо можеш відповісти на обидва питання звичайними словами, код буде коротким циклом. Такий спосіб розв'язувати задачі — розбити на менші, кожну розв'язати один раз і перевикористати відповіді — називають **динамічним програмуванням**. Далі воно знадобиться на справжній задачі диспетчерської.

```python
class Order(NamedTuple):

orders = [
```

## Мета 1: найбільше замовлень

### Ідея: звільнитися якнайраніше

Кожне замовлення «коштує» однаково: +1 до рахунку. Тоді вигідно брати те, яке **звільняє водія найраніше**: після нього залишається найбільше часу для решти.

Жадібне правило:

1. відсортувати замовлення за часом завершення;
2. йти по черзі й брати замовлення, якщо воно починається не раніше, ніж закінчилось останнє взяте;
3. ніколи не повертатися до вже прийнятих рішень.

Покроково на наших даних. Після сортування за `end`: А (10), Б (11), В (11), Г (12). `sorted` стабільний, тому Б і В з однаковим `end = 11` залишаються в початковому порядку.

```python
def max_orders(orders):
    chosen = []
    last_end = None
    for order in sorted(orders, key=lambda o: o.end):
        if last_end is None or order.start >= last_end:
            chosen.append(order)
            last_end = order.end
    return chosen


chosen = max_orders(orders)
print([o.name for o in chosen], len(chosen))
```

```text
['А', 'Б', 'Г'] 3
```

Три замовлення — більше не вийде: А, Б і Г разом займають 9:00–12:00 без пауз, а В перетинається і з А, і з Б. Сортування коштує `O(n log n)`, прохід — `O(n)`, отже весь алгоритм — `O(n log n)`.

### Чому це правило правильне

Жадібний алгоритм не перебирає варіанти, тому його правильність не очевидна — її треба **довести**. Класичний спосіб — **аргумент обміну** (exchange argument):

1. Візьмемо будь-який найкращий розклад і подивимось на його **перше** замовлення.
2. Жадібне перше замовлення закінчується **не пізніше** (воно найраніше серед усіх).
3. Замінимо перше замовлення найкращого розкладу на жадібне. Решта замовлень починалась після кінця старого першого, тож і після кінця нового — розклад лишився сумісним, а кількість не змінилась.
4. Тепер найкращий розклад починається так само, як жадібний. Повторимо міркування для решти часу — і дійдемо до жадібного розкладу, нічого не втративши.

Отже, жадібний розклад має стільки ж замовлень, скільки найкращий.

### Інші «очевидні» правила ламаються

Правило «найраніший кінець» — не єдине, що спадає на думку. Перевіримо ще два на маленьких наборах:

```python
def greedy_by(orders, key):
    """Жадібно: переглядаємо за key і беремо все, що сумісне з уже взятим."""
    chosen = []
    for order in sorted(orders, key=key):
        if all(compatible(order, c) for c in chosen):
            chosen.append(order)
    return [o.name for o in chosen]


early = [Order("Л", 8, 12, 0), Order("М", 9, 10, 0), Order("Н", 10, 11, 0)]
print("найраніший початок:", greedy_by(early, key=lambda o: o.start))
print("найраніший кінець: ", [o.name for o in max_orders(early)])

short = [Order("П", 8, 11, 0), Order("Р", 10, 12, 0), Order("С", 11, 14, 0)]
print("найкоротше:        ", greedy_by(short, key=lambda o: o.end - o.start))
print("найраніший кінець: ", [o.name for o in max_orders(short)])
```

```text
найраніший початок: ['Л']
найраніший кінець:  ['М', 'Н']
найкоротше:         ['Р']
найраніший кінець:  ['П', 'С']
```

- «Найраніший початок» бере Л (8–12), і воно блокує обидва короткі замовлення.
- «Найкоротше» бере Р (10–12, 2 години), яке перетинається з обома іншими.

Жадібні правила легко вигадати і так само легко помилитися. Тому правило або доводять, або хоча б перевіряють перебором (розділ [«Перевірка»](#brute-force)).

## Мета 2: найбільший заробіток

### «Просто бери найдорожче»?

Нове жадібне правило: переглядати замовлення від найдорожчого й брати все, що сумісне:

```python
def most_expensive_first(orders):
    return greedy_by(orders, key=lambda o: -o.reward)


print(most_expensive_first(orders))
```

```text
['В', 'Г']
```

На наших даних вийшло 750 грн — правильно. Але це збіг. Інша зміна:

```python
evening = [Order("Д", 9, 13, 500), Order("Е", 9, 11, 300), Order("Ж", 11, 13, 300)]
print(most_expensive_first(evening))
```

```text
['Д']
```

Д дає 500 грн, а Е + Ж — 600. Найдорожче замовлення забирає час у двох дешевших, які разом вигідніші.

Жадібний алгоритм робить найкращий крок **зараз** і не бачить його наслідків. Для заробітку потрібно порівнювати **цілі варіанти**: що буде, якщо взяти замовлення, і що — якщо пропустити.

## Динамічне програмування: взяти або пропустити

### Словами

Відсортуємо замовлення за часом завершення й розглядатимемо їх по одному. Для **кожного** замовлення є лише два варіанти:

- **пропустити** — тоді найкращий заробіток такий самий, як без нього;
- **взяти** — тоді отримуємо його винагороду **плюс** найкращий заробіток серед замовлень, які закінчились до його початку.

Обираємо більше. Головне: «найкращий заробіток без нього» і «найкращий серед попередніх сумісних» — це відповіді на **ту саму задачу для меншого набору**. Якщо записувати їх у таблицю, кожну рахуємо один раз.

### Позначення

Після сортування за `end` нумеруємо замовлення з **одиниці**:

| `i` | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| замовлення | А 9–10 | Б 10–11 | В 9–11 | Г 11–12 |
| у Python | `orders[0]` | `orders[1]` | `orders[2]` | `orders[3]` |

- `dp[i]` — найбільший заробіток, якщо дозволено брати лише **перші `i`** замовлень;
- `dp[0] = 0` — без замовлень заробіток нульовий (**базовий випадок**);
- `p(i)` — скільки перших замовлень закінчуються не пізніше, ніж **починається** замовлення `i`. Усі вони сумісні з ним, бо список відсортований за `end`.

Тоді для кожного `i`:

- пропустити: `dp[i - 1]`;
- взяти: `reward(i) + dp[p(i)]`;
- `dp[i] = max(пропустити, взяти)`.

Нумерація з одиниці потрібна, щоб `dp[0]` означав «жодного замовлення». Звідси зсув: замовлення `i` у Python — `orders[i - 1]`.

### Заповнюємо таблицю вручну

Спершу `p(i)`:

- А починається о 9; до 9 не закінчилось нічого → `p(1) = 0`;
- Б починається о 10; до 10 закінчилось лише А → `p(2) = 1`;
- В починається о 9 → `p(3) = 0`;
- Г починається об 11; до 11 закінчились А, Б, В → `p(4) = 3`.

Тепер рядок за рядком, **зверху вниз**: кожен рядок використовує лише вже заповнені.

| `i` | замовлення | `p(i)` | пропустити `dp[i-1]` | взяти `reward + dp[p(i)]` | `dp[i]` |
|---|---|---|---|---|---|
| 0 | — | — | — | — | **0** |
| 1 | А 200 | 0 | 0 | 200 + 0 = 200 | **200** |
| 2 | Б 200 | 1 | 200 | 200 + 200 = 400 | **400** |
| 3 | В 550 | 0 | 400 | 550 + 0 = 550 | **550** |
| 4 | Г 200 | 3 | 550 | 200 + 550 = 750 | **750** |

Відповідь — `dp[4] = 750`. Та сама таблиця як покрокова схема:

### Формула і код

Спершу `p(i)` — найпростішим способом: для кожного замовлення йти назад, доки не знайдемо перше, що закінчилось до його початку.

```python
def prev_compatible(orders):
    """p[i] для замовлень, уже відсортованих за end. p[0] не використовується."""
    p = [0] * (len(orders) + 1)
    for i in range(1, len(orders) + 1):
        start = orders[i - 1].start
        for j in range(i - 1, 0, -1):
            if orders[j - 1].end <= start:
                p[i] = j
                break
    return p


by_end = sorted(orders, key=lambda o: o.end)
print([o.name for o in by_end], prev_compatible(by_end)[1:])
```

```text
['А', 'Б', 'В', 'Г'] [0, 1, 0, 3]
```

Той самий рядок `p(i)`, що й у таблиці. Тепер сама таблиця:

```python
def max_earnings(orders):
    orders = sorted(orders, key=lambda o: o.end)
    p = prev_compatible(orders)
    dp = [0] * (len(orders) + 1)           # dp[0] = 0 — база
    for i in range(1, len(orders) + 1):    # порядок: від менших наборів до більших
        skip = dp[i - 1]
        take = orders[i - 1].reward + dp[p[i]]
        dp[i] = max(skip, take)
    return dp[-1]


print(max_earnings(orders), max_earnings(evening))
```

```text
750 600
```

750 для нашої зміни і 600 для вечірньої — там, де «бери найдорожче» дало 500.

Складність: пошук `p(i)` у гіршому разі проходить усі попередні замовлення — `O(n²)`, заповнення таблиці — `O(n)`. Прискорення до `O(n log n)` — у розділі [«Архітектура»](#architecture).

### Який розклад дав 750 { #traceback }

Число — ще не відповідь водієві: потрібен сам розклад. Його відновлюють **з кінця таблиці**: якщо в рядку `i` перемогло «взяти», замовлення `i` в розкладі, і стрибаємо в `p(i)`; інакше — переходимо до `i - 1`.

```python
def best_schedule(orders):
    orders = sorted(orders, key=lambda o: o.end)
    p = prev_compatible(orders)
    dp = [0] * (len(orders) + 1)
    for i in range(1, len(orders) + 1):
        dp[i] = max(dp[i - 1], orders[i - 1].reward + dp[p[i]])

    chosen = []
    i = len(orders)
    while i > 0:
        if orders[i - 1].reward + dp[p[i]] > dp[i - 1]:   # «взяти» перемогло
            chosen.append(orders[i - 1])
            i = p[i]
        else:                                             # «пропустити»
            i -= 1
    return list(reversed(chosen))


print([o.name for o in best_schedule(orders)])
print([o.name for o in best_schedule(evening)])
```

```python
    return max(best_plain(i - 1, orders, p),
               orders[i - 1].reward + best_plain(p[i], orders, p))


chain = [Order(f"#{k}", k, k + 2, 100) for k in range(1, 21)]
```

```python
    p = prev_compatible(orders)

    @lru_cache(maxsize=None)
    def best(i):
        if i == 0:
            return 0
        return max(best(i - 1), orders[i - 1].reward + best(p[i]))

    result = best(len(orders))
    print(best.cache_info())
    return result
```

| | Мемоізація (зверху вниз) | Табуляція (знизу вгору) |
|---|---|---|
| Напрямок | від `best(n)` до бази | від `dp[0]` до `dp[n]` |
| Код | рекурсія + кеш (`lru_cache`, словник) | цикл, що заповнює список |
| Що рахує | лише потрібні підзадачі | усі підзадачі по черзі |
| Ризик | глибина рекурсії (~1000, урок 23) | треба самому задати порядок |

### Чотири питання ДП { #four-questions }

Будь-який ДП-розв'язок відповідає на чотири питання. Для нашої задачі:

| Питання | Відповідь |
|---|---|
| **Стан** — що описує підзадачу? | `i`: дозволено брати лише перші `i` замовлень |
| **Перехід** — як відповідь складається з менших? | `dp[i] = max(dp[i-1], reward(i) + dp[p(i)])` |
| **База** — що відомо без обчислень? | `dp[0] = 0` |
| **Порядок** — у якій послідовності рахувати? | `i` від 1 до `n`: `p(i) < i`, тож усе потрібне вже пораховано |

ДП працює, коли в задачі є дві властивості:

- **оптимальна підструктура** — найкраща відповідь складається з найкращих відповідей підзадач (найкращий розклад до замовлення `i` містить найкращий розклад до `p(i)`);
- **перекриття підзадач** — ті самі підзадачі потрібні багато разів (як `best(18)` у ланцюжку чи `stairs(28)` на сходах).

!!! warning "Три міфи про ДП"
    - **«ДП — це просто кеш для будь-якої рекурсії».** Кеш допомагає, лише коли підзадачі **повторюються**. У сортуванні злиттям (урок 23) кожна половина унікальна — кешу нічого запам'ятовувати.
    - **«ДП завжди рекурсивне».** `max_earnings` — звичайний цикл без жодного рекурсивного виклику.
    - **«Таблиця ДП завжди одновимірна».** У нас стан — одне число `i`. Якщо стан описують два параметри (наприклад, замовлення й залишок пального), таблиця стає двовимірною — див. [«Матрична параметризація»](#state-dimensions).

## Перевірка повільним перебором { #brute-force }

ДП і жадібний алгоритм — хитрі. Повний перебір — тупий, але очевидно правильний: перевірити **усі** `2ⁿ` підмножини. На великих даних він безнадійно повільний, зате на малих — ідеальний суддя (урок 26: швидке рішення порівнюють з повільним).

```python
from itertools import combinations


def brute_force(orders):
    """Найбільший заробіток серед усіх сумісних підмножин. O(2ⁿ · n²)."""
    best = 0
    for size in range(len(orders) + 1):
        for combo in combinations(orders, size):
            if all(compatible(a, b) for a, b in combinations(combo, 2)):
                best = max(best, sum(o.reward for o in combo))
    return best


cases = {
    "порожній список": [],
    "усі сумісні": [Order("x", 9, 10, 100), Order("y", 10, 11, 150), Order("z", 11, 12, 50)],
    "усі перетинаються": [Order("x", 9, 12, 100), Order("y", 10, 13, 150), Order("z", 11, 14, 50)],
    "дотичні межі": orders,
    "однаковий кінець": [Order("x", 9, 11, 100), Order("y", 10, 11, 150)],
}
for name, data in cases.items():
    print(f"{name:18} ДП = {max_earnings(data):4}  перебір = {brute_force(data):4}")
```

### Складність

| Алгоритм | Час | Пам'ять | Що дає |
|---|---|---|---|
| `max_orders` (greedy) | `O(n log n)` — сортування | `O(n)` | найбільша **кількість** |
| `brute_force` | `O(2ⁿ · n²)` | `O(n)` | будь-яку мету, але лише для малих `n` |
| `max_earnings` з простим `p(i)` | `O(n²)` у гіршому разі | `O(n)` | найбільший **заробіток** |
| те саме з `bisect` для `p(i)` | `O(n log n)` | `O(n)` | те саме, швидше |

Звідки `O(n²)`? Порахуймо кроки внутрішнього циклу `prev_compatible` на найгіршому наборі — усі замовлення починаються одночасно й перетинаються:

```python
def p_steps(orders):
    steps = 0
    for i in range(1, len(orders) + 1):
        for j in range(i - 1, 0, -1):
            steps += 1
            if orders[j - 1].end <= orders[i - 1].start:
                break
    return steps


for n in (1000, 2000):
    worst = [Order(str(k), 0, k + 1, 1) for k in range(n)]
    print(n, p_steps(worst))
```

```text
2000 1999000
```

Удвічі більше замовлень — учетверо більше кроків (дослід подвоєння з уроку 9). Але `ends` відсортовані, тому `p(i)` — це кількість кінців `<= start`, тобто `bisect_right` з уроку 12: `O(log n)` на замовлення. Реалізуєш сам у «Спробуй самостійно».

??? note "Для допитливих: псевдополіноміальний час"
    У багатьох ДП-задачах таблицю будують не по об'єктах, а **по числу**: по сумі грошей (скільки монет потрібно, щоб видати `A` копійок) або по місткості рюкзака `W`. Тоді час — `O(n · A)` чи `O(n · W)`. Це схоже на поліном, але `A` може бути величезним числом, записаним лише кількома цифрами: таблиця на `10¹⁸` комірок не поміститься в жодну пам'ять. Такий час називають **псевдополіноміальним**. У нашій задачі таблиця має `n + 1` комірку — по одній на замовлення, — тож цієї пастки немає.

## Ще одна задача: решта монетами { #coins }

Сходи питали, **скільки** є способів. Багато задач питають інше — **який спосіб найкращий**: наприклад, якою найменшою кількістю монет видати суму. Для таких задач є спокуслива коротка дорога без жодної таблиці.

### Жадібно: найбільша монета, що влазить

Видаючи решту, касир бере найбільшу монету чи купюру, яка ще влазить, і повторює: 68 грн = 50 + 10 + 5 + 2 + 1. Номінали достатньо один раз відсортувати й іти від більшого до меншого:

```python
HRYVNIA = [1, 2, 5, 10, 20, 50, 100, 200, 500, 1000]


def greedy_change(amount, coins):
    used = []
    for coin in sorted(coins, reverse=True):
        while amount >= coin:
            amount -= coin
            used.append(coin)
    return used


print(greedy_change(68, HRYVNIA))
```

```text
[50, 10, 5, 2, 1]
```

Це той самий **жадібний алгоритм**, що й «найраніший кінець» у водія: на кожному кроці робить вибір, який здається найкращим зараз, і ніколи його не змінює.

### Жадібність може помилитися: шукай контрприклад

Інший набір монет — `[1, 3, 4]`:

```python
print(greedy_change(6, [1, 3, 4]))
```

```text
[4, 1, 1]
```

Три монети, а 3 + 3 — дві. Такий вхід називають **контрприкладом**, і одного досить, щоб показати: для цих монет greedy не працює. Для гривні greedy дав найкращу відповідь на кожній сумі, яку ми перевірили, а для `[1, 3, 4]` ламається вже на 6.

Чесний спосіб це знати — порівняти greedy з методом, який завжди правий, сума за сумою. Цю звичку варто тримати для будь-якого хитрого швидкого рішення, зокрема того, що запропонував ШІ-асистент: перевір його простим рішенням, якому довіряєш.

### Таблиця для монет: ті самі два питання

Метод, який для монет завжди правий, — таблиця. Ставимо ті самі два питання, що й для сходів:

1. **Що означає одна комірка?** — «`best[a]` — найменша кількість монет, якими можна скласти суму `a`».
2. **Як порахувати комірку з менших?** — «якщо остання монета `c`, потрібно `best[a - c] + 1` монет. Пробуємо кожну монету й беремо найменше».

`best[0] = 0`: суму 0 складають нуль монет. Решту комірок заповнюємо від 1 вгору:

```python
def min_coins_table(amount, coins):
    best = [float("inf")] * (amount + 1)   # inf — «поки що не можна скласти»
    best[0] = 0
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                best[a] = min(best[a], best[a - c] + 1)
    return best


print(min_coins_table(6, [1, 3, 4]))
print(min_coins_table(3, [2]))
```

```text
[0, 1, 2, 1, 1, 2, 2]
[0, inf, 1, inf]
```

Для `[1, 3, 4]` таблиця від 0 до 6 — `0, 1, 2, 1, 1, 2, 2`, тож 6 потребує двох монет. Кожна комірка стартує з `float("inf")`, що означає «поки що не можна скласти». Якщо остання комірка так і лишилась нескінченною, суму не скласти взагалі: трійку двійками не видаси.

Тепер порівняємо greedy з таблицею сума за сумою:

```python
def greedy_failures(coins, limit):
    best = min_coins_table(limit, coins)
    return [a for a in range(1, limit + 1) if len(greedy_change(a, coins)) > best[a]]


print("[1, 3, 4] до 12:", greedy_failures([1, 3, 4], 12))
print("гривня до 1000:", greedy_failures(HRYVNIA, 1000))
```

```text
[1, 3, 4] до 12: [6, 10]
гривня до 1000: []
```

Для гривні на всіх сумах до 1000 greedy збігся з таблицею. Набори монет, на яких greedy завжди найкращий, називають **канонічними**. Більшість справжніх грошових систем такі, але це властивість конкретного набору, а не жадібного алгоритму.

### Який саме набір: запам'ятати вибір

Таблиця дає число. Щоб дістати самі монети, при кожному мінімумі запам'ятовуємо, **яка монета** його дала, і йдемо назад від `amount` — як у [«Який розклад дав 750»](#traceback):

```python
def change_coins(amount, coins):
    best = [float("inf")] * (amount + 1)
    best[0] = 0
    last = [None] * (amount + 1)           # last[a] — остання монета найкращого набору для a
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a and best[a - c] + 1 < best[a]:
                best[a] = best[a - c] + 1
                last[a] = c
    if best[amount] == float("inf"):
        return None
    used = []
    while amount > 0:
        used.append(last[amount])
        amount -= last[amount]
    return used


print(change_coins(6, [1, 3, 4]), change_coins(7, [2, 4]))
```

```text
[3, 3] None
```

### Матрична параметризація: скільки змінних у стані { #state-dimensions }

Сходи, водій і монети — три ДП-задачі. Підготовку будь-якої з них зазвичай розкладають на п'ять кроків:

| Крок | Що зробити | Монети |
|---|---|---|
| 1. Параметризація | визначити, скільки змінних описує одну підзадачу, — стільки вимірів у таблиці | одна змінна: сума `a` |
| 2. Розмір простору | переконатися, що підзадач поліноміально багато, а не `2ⁿ` | `A + 1` комірка |
| 3. Порядок обходу | рахувати так, щоб менші підзадачі були готові, коли знадобляться більшим | `a` від 1 вгору: `a - c < a` |
| 4. Рекурсивна формула | як відповідь більшої задачі складається з менших | `best[a] = min(best[a - c] + 1)` |
| 5. Запам'ятати вибір | формула шукає `min`/`max`, тож зберігаємо, **який** варіант переміг | `last[a]` — остання монета |

Після підготовки йде саме обчислення: заповнити таблицю знизу вгору, зберігаючи вибір, і пройти назад від останньої комірки, щоб дістати саму відповідь, а не лише число. На практиці кроки 1–4 зводять до тих самих [чотирьох питань](#four-questions): стан, перехід, база й порядок.

Крок 1 — головний: від кількості змінних у стані залежить форма таблиці.

Ті самі монети можна описати й **двома** змінними: «скільки монет потрібно для суми `a`, якщо дозволено лише перші `k` номіналів». Тоді таблиця — матриця: рядок `k` або не бере новий номінал (`best[k - 1][a]`), або бере його ще раз (`best[k][a - c] + 1`). Для `[1, 3, 4]`:

| `k` \ `a` | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 0 — без монет | 0 | ∞ | ∞ | ∞ | ∞ | ∞ | ∞ |
| 1 — `[1]` | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| 2 — `[1, 3]` | 0 | 1 | 2 | 1 | 2 | 3 | 2 |
| 3 — `[1, 3, 4]` | 0 | 1 | 2 | 1 | 1 | 2 | 2 |

Останній рядок збігається з одновимірною таблицею: другий вимір тут не потрібен, бо будь-яку монету можна брати скільки завгодно разів. Він знадобиться, коли кожну монету можна взяти **лише раз** — це вже задача про рюкзак. Правило вибору: у стані стільки змінних, скільки потрібно, щоб підзадача мала однозначну відповідь, і не більше — кожен зайвий вимір множить розмір таблиці.

## Як читати помилки цієї теми { #errors }

| Що бачиш | Що сталося | Що робити |
|---|---|---|
| `RecursionError: maximum recursion depth exceeded`, хоча стоїть `@cache` | кеш прибирає повторну роботу, а не глибину рекурсії | перейти на таблицю (цикл) |
| `TypeError: unhashable type: 'list'` | функція з `@cache` отримала список, а кеш зберігає аргументи як ключі словника | передавати кортеж: `tuple(coins)` |
| Помилки немає, але відповідь 0 для будь-якої суми | таблицю почали нулями замість `float("inf")`, тож менше значення так і не знайшлося | `best = [float("inf")] * (amount + 1)`, лише `best[0] = 0` |
| `IndexError: list index out of range` або `list assignment index out of range` | таблиці для `n` потрібна `n + 1` комірка, від 0 до `n` | `[0] * (n + 1)` |

## Додатково: «жадібність» у регулярних виразах

Слово «жадібний» трапиться тобі ще в одному місці — у модулі `re` (урок 13). Квантифікатори `*` і `+` **жадібні**: захоплюють якомога довший шматок тексту.

```python
import re

html = "<b>Python</b><i>курс</i>"
print(re.findall(r"<.*>", html))
print(re.findall(r"<.*?>", html))
```

```text
['<b>Python</b><i>курс</i>']
['<b>', '</b>', '<i>', '</i>']
```

`.*` спершу з'їдає рядок до кінця, а потім **відступає** символ за символом (backtracking), доки не знайде `>` — останню дужку рядка. `.*?` — нежадібний: бере якомога менше.

Зверни увагу на різницю: жадібний **квантифікатор** відступає і переглядає своє рішення, а жадібний **алгоритм** — ніколи. Спільна лише назва: «брати якомога більше одразу».

### Зміни приклад: перерва між замовленнями

Водієві потрібна **година перерви** між замовленнями: після замовлення, що закінчилось о 10:00, наступне можна почати не раніше 11:00.

1. Зміни лише умову в `prev_compatible` (додай параметр `rest`, за замовчуванням 0).
2. Переконайся, що при `rest=0` усе працює як раніше, а для ранкової зміни `orders` при `rest=1` найкращий заробіток — **550 грн**.

**Критерії перевірки:**

- `max_earnings(orders, rest=0) == 750`, `max_earnings(orders, rest=1) == 550`;
- `max_earnings(shift, rest=0) == 1880`;
- `max_earnings` і `best_schedule` приймають `rest` і передають його в `prev_compatible`.

??? tip "Підказка"
    Замовлення `j` сумісне з `i`, якщо `orders[j - 1].end + rest <= start`. Чому 550? Після А (кінець о 10) можна взяти лише Г (об 11 — рівно година), 200 + 200 = 400. Б після А не можна, В + Г теж (В закінчується об 11, Г починається об 11). Лишається В саме — 550.

### Спробуй самостійно: `p(i)` через `bisect`

Напиши `max_earnings_fast(orders)`: те саме ДП, але `p(i)` знаходь через `bisect.bisect_right` по списку кінців.

**Критерії перевірки:**

- `max_earnings_fast(orders) == 750`, `max_earnings_fast(shift) == 1880`, `max_earnings_fast([]) == 0`;
- на 500 випадкових змінах результат збігається з `max_earnings` (скопіюй цикл з розділу [«Перевірка»](#brute-force));
- жодних вкладених циклів.

??? tip "Підказка"
    `ends = [o.end for o in orders]` після сортування. Кількість замовлень серед перших `i - 1`, що закінчились до `start`: `bisect.bisect_right(ends, start, 0, i - 1)`. Межа `i - 1` не дає зарахувати саме замовлення `i` чи пізніші з таким самим кінцем.

### Знайди помилку

Колега переписав сумісність «строго»:

```python
def prev_compatible_bug(orders):
    p = [0] * (len(orders) + 1)
    for i in range(1, len(orders) + 1):
        for j in range(i - 1, 0, -1):
            if orders[j - 1].end < orders[i - 1].start:
                p[i] = j
                break
    return p


by_end = sorted(orders, key=lambda o: o.end)
p_bug = prev_compatible_bug(by_end)
dp = [0] * 5
for i in range(1, 5):
    dp[i] = max(dp[i - 1], by_end[i - 1].reward + dp[p_bug[i]])
print(p_bug[1:], dp[4])
```

```text
[0, 0, 0, 1] 550
```

??? question "Що не так і чому саме 550?"
    Порівняй `p` з таблицею й перевір, які замовлення тепер вважаються несумісними.

??? success "Відповідь"
    `<` замість `<=` порушує правило моделі «закінчилось о 10:00 — можна почати о 10:00». Тепер Г (початок 11) не можна поставити після Б чи В (кінець 11): `p(4) = 1` замість 3. Найкращим стає В саме — 550. Помилка на межі: такі ловлять тести з дотичними інтервалами (набір «дотичні межі» в розділі «Перевірка»).

| Аргумент обміну | заміна першого кроку оптимального розв'язку на жадібний нічого не погіршує |
| Зміна мети | правило для кількості не працює для заробітку; «найдорожче» — теж |
| ДП | стан · перехід · база · порядок; кожна підзадача рахується один раз |
| Взяти або пропустити | `dp[i] = max(dp[i-1], reward(i) + dp[p(i)])` |
| Відновлення відповіді | іти по таблиці з кінця: «взяти» → `p(i)`, «пропустити» → `i - 1` |
| Мемоізація й табуляція | та сама формула: рекурсія з `@cache` / `lru_cache` або цикл по таблиці; кеш не прибирає глибину |
| Два питання перед таблицею | що означає одна комірка? як її порахувати з попередніх? |
| Параметризація | скільки змінних у стані — стільки вимірів у таблиці; комірок має бути поліноміально багато |
| Перевірка | швидке рішення порівнюють з перебором на малих і граничних даних |

### Терміни

**Динамічне програмування (ДП)** — розв'язання задачі через менші: кожну розв'язати один раз і перевикористати відповіді. Сьогодні: сходи, заробіток водія, найменше монет.

**Перекриття підзадач** (overlapping subproblems) — те саме менше питання трапляється багато разів усередині більшого, як `stairs(28)` у `stairs(30)`. Знак того, що відповіді варто запам'ятати.

**Мемоізація** — зберегти результат виклику функції й наступного разу повернути його, не рахуючи знову; `@functools.cache` робить це за тебе.

**Табуляція** — заповнення таблиці відповідей циклом, від найменшого випадку вгору, без рекурсії.

**Жадібний алгоритм** — алгоритм, який на кожному кроці робить вибір, що здається найкращим, і ніколи його не скасовує, як «спершу найбільша монета».

**Контрприклад** — один конкретний вхід, на якому алгоритм дає неправильну відповідь; для жадібної решти монетами `[1, 3, 4]` — сума 6.

**Матрична параметризація** — вибір змінних, що описують підзадачу: одна змінна дає рядок `dp[i]`, дві — матрицю `dp[i][j]`.
